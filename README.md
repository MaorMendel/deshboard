# דשבורד הבוט ללקוחות

כל לקוח מקבל קישור אישי. בקישור הזה הוא בוחר קול, קובע מי מדבר ראשון, עורך את הפתיח, את משפט הסגירה ואת ההנחיות לבוט, מנסה את הבוט בשיחה לטלפון שלו, ומעדכן את הבוט החי. מאחורי הקלעים כל שינוי עובר ל-assistant שלו ב-Vapi.

יש שני סוגי לקוחות:

- **לקוח משלם:** "עדכן את הבוט" משנה את ה-assistant שלו ב-Vapi. כל השיחות שלו, כולל שיחות ניסיון, נספרות לחיוב שנעשה במערכת הראשית שלך.
- **דמו:** ליד שמשחק עם הבוט. השיחות רצות על assistant משותף, עם מגבלה של כמה דקות (ברירת מחדל 5) ותאריך תפוגה (ברירת מחדל שבוע). כשהוא הופך ללקוח, מה שהגדר בדמו עובר ל-assistant שלו.

## איך זה עובד

```
לקוח  ──>  https://<האתר>/b/<מפתח>  ──>  השרת (Next.js)  ──>  Vapi
                                        │
                                        └──>  Supabase (Postgres)

המערכת שלך  ──>  /api/internal/usage  (דקות לחיוב)
cron        ──>  /api/internal/sync-calls  (מושך שיחות מ-Vapi)
```

- **הקישור האישי** הוא הכניסה. המפתח שבו אקראי (43 תווים), וב-DB נשמר רק ה-hash שלו. השרת מוצא לפיו את הלקוח. הדפדפן אף פעם לא שולח מזהה לקוח או מזהה assistant.
- **"עדכן את הבוט"** שומר גרסה חדשה ב-DB, ואצל לקוח משלם גם שולח ל-assistant ב-Vapi את השדות שהשתנו. אם Vapi נכשל, שום דבר לא נשמר והלקוח מקבל הודעה ברורה.
- **המסך מציג את מה שחי ב-Vapi.** גם שינוי שנעשה ישירות ב-Vapi או בפאנל הניהול מופיע אצל הלקוח ברענון.
- **"נסה את הבוט"** מתקשר לטלפון המאומת של בעל העסק עם ההגדרות שעל המסך, גם אם עוד לא עודכנו. הבוט החי לא משתנה. לכל לקוח יכולה להיות רק שיחת ניסיון פעילה אחת בכל רגע.
- **שיחות** נמשכות מ-Vapi אל טבלת `calls`: משך, עלות וסיבת סיום. מהטבלה הזו מחושבות הדקות.

## הקמה ראשונה

מה שכבר בוצע: פרויקט Supabase בשם `bot-dashboard-eu` בפרנקפורט, עם כל הטבלאות, ה-Data API כבוי ו-RLS פעיל.

1. **להתקין:** Node.js 20 ומעלה, ואז בתיקיית הפרויקט:
   ```bash
   npm install
   ```
2. **להגדיר משתני סביבה:** להעתיק את `.env.example` ל-`.env` ולמלא. הפירוט בפרק הבא.
3. **להכין ב-Vapi:**
   - **assistant לדמואים:** assistant כללי שעליו ירוצו כל הדמואים, עם פרומפט כללי שמתאים לכל עסק. את ה-ID שלו שמים ב-`VAPI_DEMO_ASSISTANT_ID`.
   - **מספר לשיחות ניסיון:** מספר שיכול להתקשר לישראל. את ה-ID שלו שמים ב-`VAPI_TEST_PHONE_NUMBER_ID`.
4. **לייבא קולות:**
   ```bash
   npm run voices:import
   ```
   ואז לתת להם שמות ולהפעיל אותם. ההסבר בפרק [קולות](#קולות).
5. **לחבר את הלקוח הראשון:**
   ```bash
   npm run customer:add -- --name "מספרת רוני" --external-id 1001 --assistant <assistantId> --phone-number <phoneNumberId> --bot-phone "04-555-0182" --test-phone 0501234567
   ```
   הפקודה מדפיסה את הקישור האישי. הוא מוצג רק פעם אחת, אז כדאי לשלוח אותו ללקוח מיד.
6. **להעלות לאוויר:** ההסבר בפרק [העלאה לאוויר](#העלאה-לאוויר).

## משתני סביבה

| משתנה | מה זה | מאיפה מביאים |
| --- | --- | --- |
| `APP_URL` | הכתובת הציבורית של האתר. ממנה נבנים הקישורים. | הדומיין שתעלה עליו, למשל `https://bots.example.com` |
| `DATABASE_URL` | החיבור ל-Supabase | Supabase → הפרויקט → **Connect** → **Shared Pooler**. מחליפים את `[YOUR-PASSWORD]` בסיסמה ששמרת |
| `VAPI_PRIVATE_KEY` | המפתח הפרטי של Vapi | Vapi Dashboard → **API Keys** → Private Key |
| `VAPI_DEMO_ASSISTANT_ID` | ה-assistant המשותף של הדמואים | Vapi → Assistants → ה-ID בעמוד ה-assistant |
| `VAPI_TEST_PHONE_NUMBER_ID` | המספר שממנו יוצאות שיחות ניסיון של דמואים, ושל לקוחות שאין להם מספר משלהם | Vapi → Phone Numbers → ה-ID של המספר |
| `ADMIN_PASSWORD` | הסיסמה של פאנל הניהול (`/admin`), לפחות 8 תווים. בלעדיה הפאנל כבוי | לבחור סיסמה חזקה |
| `INTERNAL_API_SECRET` | סוד משותף בין האתר למערכת שלך. משמש גם להצפנת הקישורים כדי שהפאנל יוכל להציג אותם שוב | ליצור: `openssl rand -hex 32` |
| `ELEVENLABS_API_KEY` | (לא חובה) ליצירת דוגמאות שמע לקולות של ElevenLabs. בלעדיו מעלים MP3 ידנית | elevenlabs.io → Developers → API Keys (הרשאת Text to Speech מספיקה) |
| `CARTESIA_API_KEY` | (לא חובה) ליצירת דוגמאות שמע לקולות של Cartesia, ול-`voices:add` | play.cartesia.ai → API Keys |
| `DATABASE_POOL_MAX` | (לא חובה) כמה חיבורים פתוחים ל-DB. ברירת מחדל 10 | |

**חשוב על המספר לשיחות ניסיון:** מספרים חינמיים של Vapi לא יכולים להתקשר למספרים בחו"ל, ולכן לא יגיעו לטלפון ישראלי. צריך מספר מ-Twilio, מ-Vonage או מ-SIP שמחובר ל-Vapi. אצל לקוח משלם שיש לו מספר משלו (`--phone-number`), שיחת הניסיון יוצאת מהמספר שלו.

## ניהול שוטף

### פאנל הניהול

ב-`https://<האתר>/admin`, עם הסיסמה שב-`ADMIN_PASSWORD`. משם עושים הכול:

- **לקוח חדש / דמו חדש**, כולל בחירת assistant ומספר מתוך רשימות מ-Vapi. הקישור האישי מוצג פעם אחת, עם כפתור העתקה.
- **חבילה לכל לקוח:** ממתי היא נספרת וכמה דקות יש בה בחודש. המונה מתאפס כל חודש באותו יום. הלקוח רואה בדף שלו כמה ניצל, ואתה רואה את אותו מספר ברשימה ובעמוד הלקוח. הדקות מחושבות מסך השניות של כל השיחות במחזור: 195 שניות הן 3 דקות, ושיחה של שנייה אחת לא מוסיפה דקה. ה-API הפנימי ממשיך להחזיר גם את החישוב המעוגל לחיוב.
- **קישורים:** הנפקה (עם או בלי ביטול הקודמים), ביטול, הצגת הקישור של כל לקוח, ותאריך שימוש אחרון.
- **השעיה והחזרה לפעילות**, והמרת דמו ללקוח משלם.
- **עריכת הפרומפט** של ה-assistant (הודעת ה-system ב-Vapi). שאר הגדרות ה-model, הכלים וה-webhooks לא נגעים.
- **שיחות אחרונות** של כל לקוח, עם המחיר של כל שיחה.
- **עלות לכל לקוח:** כמה Vapi חייב אותך על השיחות שלו. ברשימה: הסכום בתקופה הנוכחית. בעמוד הלקוח: הסכום, העלות לדקה, ההשוואה לתקופה הקודמת, ופירוט לפי רכיב (מודל השפה, הקול, תמלול, טלפוניה, העמלה של Vapi, ניתוח אחרי השיחה). פירוט בפרק [עלות](#עלות).
- **קולות** (בתפריט למעלה): הוספת קול של ElevenLabs או Cartesia, שם ותיאור, מודל ומהירות, דוגמאות שמע, והחלת שינוי על ה-assistants. פירוט בפרק [קולות](#קולות).

**assistant חדש שהוספת ב-Vapi לא מופיע בתפריט?** הרשימה נשמרת לכמה דקות. הקישור "רענון מ-Vapi" שמתחת לתפריט טוען אותה מחדש מיד. assistant שכבר מחובר ללקוח (או ה-assistant של הדמואים) מופיע אפור ואי אפשר לבחור בו, והשרת חוסם את זה גם אם מנסים בכל זאת.

הכניסה נשמרת בעוגייה ל-30 יום. החלפת `ADMIN_PASSWORD` מנתקת מיד את כל מי שמחובר.

### פקודות

אותן פעולות קיימות גם כפקודות מתיקיית הפרויקט, עם `.env` מוגדר. הפאנל והפקודות משתמשים באותו קוד בדיוק.

### לחבר לקוח קיים

```bash
npm run customer:add -- --name "מספרת רוני" --external-id 1001 --assistant <assistantId> \
  --phone-number <phoneNumberId> --bot-phone "04-555-0182" --test-phone 0501234567
```

- `--external-id`: המזהה של הלקוח **במערכת שלך**. לפיו המערכת שלך מבקשת את הדקות.
- `--assistant`: ה-assistant של הלקוח ב-Vapi.
- `--phone-number` (לא חובה): ה-ID של המספר שהבוט עונה בו. שיחות ניסיון יוצאות ממנו.
- `--bot-phone` (לא חובה): המספר כפי שהלקוח מכיר אותו, לתצוגה בראש הדף.
- `--test-phone` (לא חובה, אבל בלעדיו אין שיחות ניסיון): הטלפון של בעל העסק. שיחות ניסיון מגיעות רק אליו, והלקוח לא יכול לשנות את המספר הזה.

הפקודה קוראת מ-Vapi את ההגדרות הנוכחיות של ה-assistant (קול, פתיח, סגירה, מי מדבר ראשון) ושומרת אותן כגרסה הראשונה. כשהלקוח נכנס, הוא רואה בדיוק את מה שהבוט עושה היום.

### ליצור דמו

```bash
npm run demo:add -- --name "קליניקת שקד" --test-phone 0521234567 --minutes 5 --days 7
```

הפקודה מדפיסה את הקישור ואת ה-id של הדמו, שצריך לשמור בשביל ההמרה. `--minutes` ו-`--days` לא חובה, וברירת המחדל שלהם 5 ו-7.

### להפוך דמו ללקוח משלם

```bash
npm run demo:convert -- --tenant <id של הדמו> --external-id 1002 --assistant <assistantId> --phone-number <phoneNumberId>
```

הקול, הפתיח והסגירה שהלקוח הגדיר בדמו נשלחים ל-assistant שלו, והקישור שכבר יש לו ממשיך לעבוד.

### קישורים

```bash
npm run link:new -- --tenant 1001                         # קישור חדש, הקודמים מבוטלים
npm run link:new -- --tenant 1001 --label "המזכירה" --keep-old   # קישור נוסף, הקודמים נשארים
npm run link:revoke -- --tenant 1001                      # ביטול כל הקישורים
```

`--tenant` מקבל את המזהה במערכת שלך, או את ה-id הפנימי (בדמואים).

קישור שבוטל מפסיק לעבוד מיד, ואי אפשר להחזיר אותו.

**לראות קישור קיים:** בפאנל הניהול, בעמוד הלקוח, בעמודה "הקישור". זה עובד כי לכל קישור נשמר גם עותק מוצפן (AES-256-GCM, המפתח נגזר מ-`INTERNAL_API_SECRET`), שנפתח רק בשרת. קישורים שנוצרו לפני השינוי הזה, וקישורים שנוצרו כש-`INTERNAL_API_SECRET` לא היה מוגדר, מופיעים כ"לא זמין לצפייה" - להם צריך להנפיק קישור חדש. אם מחליפים את `INTERNAL_API_SECRET`, הקישורים ממשיכים לעבוד אבל אי אפשר יותר להציג אותם.

### השעיה

```bash
npm run tenant:suspend -- --tenant 1001
npm run tenant:activate -- --tenant 1001
```

לקוח מושהה רואה "החשבון מושהה" ולא יכול לשנות כלום. הבוט שלו ב-Vapi ממשיך לעבוד כרגיל. ההשעיה חוסמת רק את הדשבורד.

## קולות

הקולות שהלקוחות רואים מגיעים מטבלת `voices`. הלקוח רואה רק שם, תיאור ודוגמת שמע, ושולח לשרת רק את המזהה הקצר של הקול (למשל `11labs-abc123`). הספק, ה-ID אצל הספק, המודל והכיוונונים שמורים בטבלה, והשרת בונה מהם את הקול שנשלח ל-Vapi. מי שמעתיק את הבקשה מהדפדפן ומוסיף לה מודל או קול אחר, השרת פשוט מתעלם מהשדות האלה (יש על זה בדיקה ב-`check:e2e`).

### להוסיף קול מפאנל הניהול

`/admin/voices` → **הוספת קול**:

1. **ספק:** ElevenLabs או Cartesia.
2. **Voice ID:** ב-ElevenLabs: Voices → הקול → Copy voice ID. ב-Cartesia: הקול → Copy ID.
3. **השם שהלקוחות יראו**, מגדר ותיאור קצר.
4. **מודל:** הרשימה היא בדיוק מה ש-Vapi מקבל. לעברית ב-ElevenLabs: `eleven_v3` (לפי ElevenLabs, `eleven_multilingual_v2` ו-`eleven_flash_v2_5` לא תומכים בעברית).
5. מהירות ו-stability: לא חובה. ריק = ברירת המחדל.

אחרי ההוספה נוצרת דוגמת שמע אוטומטית, אם יש בשרת `ELEVENLABS_API_KEY` (או `CARTESIA_API_KEY` לקולות של Cartesia). אם הדוגמה לא נוצרת, כנראה שה-ID או המודל לא נכונים. בלי מפתח, מעלים MP3 ידנית.

**כדי שקול של ElevenLabs יעבוד בשיחות:** ElevenLabs צריך להיות מחובר ב-Vapi (Integrations), והקול צריך להיות זמין בחשבון ElevenLabs המחובר (קול מה-Voice Library: להוסיף אותו ל-My Voices).

**עריכה:** בכל קול → "עריכה": שם, תיאור, רמה, סדר, הצגה ללקוחות, מודל ומהירות. שינוי מודל או מהירות חל מיד על כל לקוח שבוחר את הקול מעכשיו ועל שיחות ניסיון. **בוטים שכבר מדברים בקול** ממשיכים עם ההגדרה הקודמת, עד שלוחצים "להחיל את ההגדרות על כל ה-assistants שמשתמשים בו". הכפתור בודק ב-Vapi אילו assistants מדברים בקול הזה עכשיו, ומעדכן רק אותם.

### להוסיף קול מהטרמינל (Cartesia)

לוקחים את ה-ID של הקול מ-Cartesia (play.cartesia.ai → Voices) ומריצים:

```bash
npm run voices:add -- --voice <ID מ-Cartesia> --name "גיל" --description "ענייני ורגוע"
```

הפקודה מאמתת את הקול מול Cartesia, מוסיפה אותו לקטלוג **פעיל**, ומייצרת לו דוגמת שמע. אין צורך להגדיר אותו על assistant, ואין צורך לגעת ב-Supabase.

| דגל | מה הוא עושה |
| --- | --- |
| `--name`, `--description` | מה שהלקוח רואה. בלעדיהם נלקחים מ-Cartesia |
| `--gender female\|male` | חובה רק אם ב-Cartesia לא מוגדר מגדר. קובע אם המסך כותב "נועה אומרת" או "איתי אומר" |
| `--tier premium` | תווית ליד הקול |
| `--order 10` | הסדר ברשימה. מספר קטן מופיע קודם |
| `--speed 1.1`, `--model sonic-3.5` | כיוונון הקול |
| `--inactive` | להוסיף בלי להציע ללקוחות |

**לשנות קול קיים:** אותה פקודה עם אותו ID. משתנה רק מה שהעברת, כך ש-`--name` לבד לא נוגע בתיאור. דוגמת שמע נוצרת מחדש רק אם שינית `--model`, `--speed` או `--text`.

**לכבות קול:** `npm run voices:add -- --voice <ID> --inactive`. לא מוחקים קולות, כי גרסאות שמורות מצביעות עליהם. לקוח שהקול שלו כובה ממשיך לראות אותו, ולקוחות אחרים לא יכולים לבחור בו.

### לייבא קולות מ-assistants קיימים

```bash
npm run voices:import
```

הפקודה עוברת על כל ה-assistants בחשבון, ולכל קול שונה שהיא מוצאת יוצרת שורה בטבלה, **כבויה ובלי שם**. בשורה נשמרות כל ההגדרות של הקול כמו שהן ב-Vapi (מודל, שפה, speed וכו'), כך שהחלפת קול אצל לקוח לא מוחקת את הכיוונונים.

כדי להפעיל קול כזה, הדרך הקצרה היא להריץ עליו `voices:add` עם ה-ID שלו: הוא יקבל שם, תיאור, דוגמת שמע, וידלק. לחלופין, ב-Supabase → **Table Editor** → `voices`:

| עמודה | מה לשים |
| --- | --- |
| `name` | שם שהלקוח יראה, למשל "נועה" |
| `gender` | `female` או `male`. קובע אם המסך כותב "נועה אומרת" או "איתי אומר" |
| `description` | תיאור קצר, למשל "חמה ורגועה" |
| `tier` | `standard` או `premium`. כרגע רק תווית שמוצגת ליד הקול |
| `sort_order` | הסדר ברשימה. מספר קטן מופיע קודם |
| `sample_url` | (לא חובה) כתובת של קובץ שמע לדוגמה. בלעדיו, כפתור ההשמעה מציע לנסות בשיחת ניסיון |
| `is_active` | `true` כדי שיופיע אצל הלקוחות |

**שימו לב:** ב-DB יש 6 קולות לדוגמה (נועה, איתי וכו') עם `provider_voice_id = REPLACE_ME`, שאינם קולות אמיתיים. הם כבויים, וכדאי להשאיר אותם כך.

### דוגמאות שמע

כשהלקוח לוחץ ▶ ליד קול, הוא שומע משפט קצר בקול הזה. שתי דרכים ליצור דוגמה, שתיהן מפאנל הניהול (`/admin/voices`, בכל קול):

- **"ליצור דוגמה":** נוצרת אצל הספק (ElevenLabs או Cartesia) עם אותן הגדרות שיש לקול ב-Vapi: מודל, מהירות, stability. צריך `ELEVENLABS_API_KEY` או `CARTESIA_API_KEY` בשרת. מפתח של ElevenLabs עם הרשאת Text to Speech מספיק.
- **"להעלות MP3":** לכל קול מכל ספק. רק MP3, עד 2MB (משפט של 10-20 שניות הוא בערך 200KB). השרת בודק שזה באמת MP3 לפני שהוא שומר.

הלקוח אף פעם לא גורם ליצירה של דוגמה. הוא רק מאזין לקובץ ששמור. כך אי אפשר להריץ על חשבונך יצירת קול מבחוץ.

אותו דבר מהטרמינל:

```bash
npm run voices:samples                                # לכל קול שעוד אין לו דוגמה
npm run voices:samples -- --voice <id> --force        # מחדש לקול אחד
npm run voices:samples -- --force --text "משפט אחר"   # מחדש לכולם, עם משפט אחר
```

- צריך `CARTESIA_API_KEY` או `ELEVENLABS_API_KEY` ב-`.env`, לפי הספק של הקול.
- **הדוגמה נשמרת בטבלת `voices` עצמה** (עמודת `sample_audio`), ומוגשת מ-`/api/voice-samples/<id>`. לכן היא זמינה מיד, בלי להפעיל מחדש את השרת ובלי להעלות קבצים. אפשר להריץ את הפקודה מהמחשב מול ה-DB של פרודקשן, והקול יישמע שם מיד.
- המודל נלקח מהקול ב-Vapi. אם לא מוגדר שם: `sonic-3.6` ב-Cartesia, `eleven_turbo_v2_5` ב-ElevenLabs (כדאי לקבוע מודל במסך הקולות, כדי שהדוגמה תישמע בדיוק כמו בשיחה). אפשר לעקוף: `--model ...`.
- קול מספק אחר: מעלים MP3 במסך הקולות.

> לא לשמור דוגמאות שמע בתיקיית `public`: Next מאנדקס אותה כשהשרת עולה, ולכן קובץ שנוצר אחר כך מחזיר 404 עד הפעלה מחדש, ובפרודקשן (למשל Vercel) אין בכלל אפשרות לכתוב לדיסק.

## החיבור ל-Vapi

**מה המערכת משנה ב-assistant של לקוח** (רק כשהוא לוחץ "עדכן את הבוט"):

| במסך | ב-Vapi |
| --- | --- |
| הקול | `voice`: אובייקט מלא עם כל ההגדרות של הקול מהקטלוג |
| מי מדבר ראשון | `firstMessageMode`: `assistant-speaks-first` או `assistant-waits-for-user` |
| פתיח | `firstMessage`. ריק + "הבוט מדבר ראשון" = `assistant-speaks-first-with-model-generated-message`, כלומר הבוט פותח במשפט שהמודל מחבר מההנחיות |
| סגירה | `endCallMessage`: נאמר רק כשהבוט מסיים את השיחה בעצמו. ריק = מנתק בלי משפט |
| ההנחיות | `model.messages`: רק התוכן של הודעת ה-`system` מוחלף. ריק = לא נוגעים בהנחיות הקיימות |

**מה המערכת לא נוגעת בו:** המודל עצמו, הטמפרטורה, הכלים, ה-`server` (webhooks), שאר ההודעות וכל שאר ההגדרות. בעדכון הנחיות ה-`model` נשלח בשלמותו, עם ההודעות הקיימות, כך ששום הגדרה אחרת לא נמחקת. אם ה-assistants שלך שולחים webhooks למערכת שלך, הם ממשיכים בדיוק כמו קודם. את נתוני השיחות המערכת מושכת דרך ה-API של Vapi.

**שיחת ניסיון** נוצרת עם `POST /call`, עם `assistantOverrides` שמכילים את ההגדרות שעל המסך. אצל לקוח משלם היא רצה על ה-assistant שלו, ובדמו על ה-assistant המשותף, עם `maxDurationSeconds` לפי מה שנשאר מדקות הדמו.

**משתנים:** אם בפתיח יש משתנים כמו `{{customer.name}}`, הם נשמרים ועוברים כמו שהם.

**לבדוק בשיחה הראשונה:** במצב "המתקשר מדבר ראשון" (`assistant-waits-for-user`), התיעוד של Vapi לא מבהיר אם הפתיח מושמע אחרי שהמתקשר מדבר. כדאי לבדוק בשיחת ניסיון אחת.

**ה-assistant ב-Vapi הוא מקור האמת.** המסך של הלקוח קורא ממנו בכל טעינה את הקול, מי מדבר ראשון, הפתיח, הסגירה וההנחיות. לכן שינוי שאתה עושה ישירות ב-Vapi מופיע אצל הלקוח ברענון. טבלת `bot_versions` היא היסטוריה של מה שהלקוח שמר, ולא המקור לתצוגה. אם Vapi לא זמין באותו רגע, המסך מציג את הגרסה האחרונה שנשמרה אצלנו.

**לא נדרסים שינויים שלך.** בעדכון, הדפדפן שולח גם את ההגדרות שהוא טען (`baseline`), והשרת כותב ל-Vapi **רק את השדות שהלקוח באמת שינה**. אם הלקוח החליף קול בלבד, הפתיח וההנחיות לא נשלחים בכלל. כך מסך שהיה פתוח מזמן לא מחזיר אחורה שינוי שעשית בינתיים ב-Vapi או בפאנל הניהול.

**קול שלא בקטלוג:** אם תגדיר ב-Vapi קול שאין בטבלת `voices`, המסך לא יוכל לסמן אותו ויציג את הקול השמור האחרון. להוסיף אותו: `npm run voices:add -- --voice <ID>`.

**מהירות:** כל קריאה ל-API של Vapi לוקחת בין חצי שנייה לשתיים (`GET /call` הוא האיטי ביניהם). לכן משיכת השיחות של לקוח לא רצה יותר מפעם בדקה, ורשימות ה-assistants והמספרים בפאנל נשמרות בזיכרון לחמש דקות. תשובות שמוצגות למשתמש וחוזרות אלינו בעדכון הבא לא נשמרות בזיכרון בכלל, כדי שלא יידרס מידע עדכני.

## הדקות והחיבור למערכת שלך

### דקות של לקוח

```
GET /api/internal/usage?customer=<external_customer_id>&from=<ISO>&to=<ISO>
Authorization: Bearer <INTERNAL_API_SECRET>
```

דוגמה:

```bash
curl -H "Authorization: Bearer $INTERNAL_API_SECRET" \
  "https://bots.example.com/api/internal/usage?customer=1001&from=2026-10-01T00:00:00%2B03:00&to=2026-11-01T00:00:00%2B02:00"
```

תשובה:

```json
{
  "externalCustomerId": "1001",
  "from": "2026-09-30T21:00:00.000Z",
  "to": "2026-10-31T22:00:00.000Z",
  "realSeconds": 5400,
  "testSeconds": 240,
  "totalSeconds": 5640,
  "totalMinutesRoundedPerCall": 101,
  "callCount": 88,
  "vapiCostUsd": 12.34
}
```

- `realSeconds`: שיחות אמיתיות, נכנסות ויוצאות.
- `testSeconds`: שיחות ניסיון מהדשבורד.
- `totalMinutesRoundedPerCall`: כל שיחה מעוגלת למעלה לדקה שלמה, ואז סכום. אם אתה מחייב לפי שניות, להשתמש ב-`totalSeconds`.
- `vapiCostUsd`: כמה Vapi חייב אותך על השיחות האלה, כדי שתוכל לראות את הרווח.
- נספרות רק שיחות שהסתיימו, לפי זמן תחילת השיחה. `from` כלול בטווח, `to` לא.
- לפני החישוב המערכת מושכת מ-Vapi את השיחות של הטווח, כדי שהמספרים יהיו עדכניים. אפשר לכבות את זה עם `&sync=0`.
- לקוח לא קיים מחזיר 404. בלי הסוד, או עם סוד שגוי, מתקבל 401.

החבילות, החריגות והחיוב עצמו נשארים במערכת שלך. האתר רק מחזיר את המספרים.

### עלות

העלות היא מה ש-Vapi מדווח על כל שיחה (`cost` ו-`costBreakdown`), בדולרים. היא נשמרת בטבלת `calls` יחד עם הדקות, באותו סנכרון.

- **התקופה:** אותה תקופה שבה נספרות הדקות של הלקוח, כדי ששני המספרים יתאימו: מחזור החבילה. לקוח בלי חבילה: החודש הקלנדרי (שעון ישראל). דמו: כל הדמו.
- **מה נכלל:** כל השיחות של הלקוח, כולל שיחות ניסיון ושיחות יוצאות שלא נענו (גם להן יש מחיר קטן). שיחה נספרת לפי זמן תחילתה, ואם לא התחילה, לפי זמן יצירתה.
- **"לא מפורט":** שיחות שסונכרנו לפני ששמרנו את הפירוט. כשנכנסים לעמוד הלקוח, השיחות של התקופה הנוכחית מסונכרנות מחדש ומקבלות פירוט.
- **ספק עם מפתח משלך:** ספק שמחובר ב-Vapi עם מפתח משלך (למשל ElevenLabs, או מספר Twilio משלך) עשוי לחייב אותך ישירות. במקרה כזה החלק שלו לא נכלל בסכום של Vapi, וצריך לבדוק אותו אצל הספק.
- **דמואים:** השיחות שלהם רצות על ה-assistant המשותף. העלות הסופית של שיחה (כולל הסיכום שאחריה) מגיעה מ-Vapi קצת אחרי הסיום, ולכן היא מתעדכנת בסנכרון (`/api/internal/sync-calls`) ובכניסה לעמוד הדמו.
- **ברשימת הלקוחות** הסכום הוא מה שכבר מסונכרן. הוא מתעדכן בסנכרון התקופתי, בכניסה לעמוד הלקוח, וכשהלקוח עצמו נכנס לדף שלו.

### סנכרון שיחות

```
POST /api/internal/sync-calls?hours=24
Authorization: Bearer <INTERNAL_API_SECRET>
```

מושך מ-Vapi את כל השיחות שהשתנו ב-`hours` השעות האחרונות (עד 62 ימים), לכל הלקוחות המשלמים. כדאי להריץ כל 5 עד 10 דקות, למשל עם cron בשרת:

```
*/10 * * * * curl -s -X POST -H "Authorization: Bearer <סוד>" "https://bots.example.com/api/internal/sync-calls?hours=2"
```

אפשר גם ידנית: `npm run calls:sync -- --hours 24`.

בלי הסנכרון שום דבר לא נשבר: חישוב הדקות מסנכרן בעצמו, ושיחות ניסיון מתעדכנות בכל פעם שהלקוח מנסה שוב. הסנכרון שומר את טבלת `calls` עדכנית, למשל בשביל מי שמסתכל עליה ב-Supabase.

## העלאה לאוויר

הדבר היחיד שחייב להיות זהה בכל דרך: כל משתני הסביבה מוגדרים, ו-`APP_URL` מצביע על הכתובת האמיתית.

### על השרת שלך

```bash
npm ci
npm run build
npm start -- -p 3100        # פורט לבחירתך
```

- **להשאיר רץ:** עם `pm2` (`pm2 start npm --name bot-dashboard -- start -- -p 3100`) או עם systemd.
- **להפנות דומיין:** עם nginx או Caddy, דומיין או סאב-דומיין (למשל `bots.yourdomain.co.il`), עם HTTPS. בלי HTTPS הקישורים האישיים עוברים ברשת בלי הצפנה.
- **cron** לסנכרון השיחות, כמו בפרק הקודם.

### ב-Vercel

1. לחבר את הריפו ב-Vercel.
2. להגדיר את כל משתני הסביבה ב-Settings → Environment Variables.
3. לסנכרון השיחות: Vercel Cron או כל שירות cron חיצוני שקורא ל-`/api/internal/sync-calls`.
4. Vercel לא מריץ מיגרציות. אחרי עדכון שמוסיף קובץ ל-`drizzle/`, מריצים `npm run db:migrate` מהמחשב (ראו "עדכון גרסה").

### עדכון גרסה

```bash
git pull && npm ci && npm run db:migrate && npm run build && pm2 restart bot-dashboard
```

`npm run db:migrate` מריץ רק מיגרציות חדשות, אם יש.

**חשוב:** כשעדכון מוסיף קובץ חדש בתיקייה `drizzle/`, צריך להריץ `npm run db:migrate` מול ה-DB של פרודקשן לפני שמשתמשים בגרסה החדשה, גם ב-Vercel וגם כשמריצים על המחשב (`npm run dev`). מספיק להריץ מהמחשב, מתיקיית הפרויקט, עם `DATABASE_URL` של Supabase ב-`.env`. בלי זה, קוד חדש פונה לעמודות שעוד לא קיימות: עמוד הלקוח בפאנל יציג הודעה במקום העלות, והסנכרון של שיחות ודקות מ-Vapi ייכשל בשקט.

## ה-DB

Postgres ב-Supabase, עם Drizzle ORM. הסכמה נמצאת ב-`src/db/schema.ts`, והמיגרציות בתיקיית `drizzle/`.

| טבלה | מה יש בה |
| --- | --- |
| `tenants` | העסקים: מזהה במערכת שלך, לקוח או דמו, מגבלות דמו, מזהי Vapi, טלפון לשיחות ניסיון, הגרסה הנוכחית |
| `bot_versions` | כל עדכון של כל בוט: ההגדרות ומה שנשלח ל-Vapi. שורות לא נמחקות ולא נערכות |
| `voices` | קטלוג הקולות, כולל ההגדרות המלאות מ-Vapi |
| `access_links` | הקישורים: hash של המפתח, תווית, ביטול, שימוש אחרון |
| `calls` | כל שיחה, אמיתית או ניסיון: משך, עלות, סיבת סיום |
| `audit_log` | כל פעולה: מי, מה, מצב לפני ואחרי, IP |

**שינוי בסכמה:** עורכים את `schema.ts`, ואז:

```bash
npm run db:generate   # יוצר קובץ מיגרציה חדש
npm run db:migrate    # מריץ אותו על Supabase
```

**לעריכה ידנית ב-Table Editor** בטוחות העמודות התיאוריות של `voices` (שם, מגדר, תיאור, סדר, `is_active`), אבל את כולן אפשר לערוך גם במסך הקולות בפאנל. את שאר הטבלאות עדיף לשנות רק דרך הפקודות, ובהמשך דרך פאנל הניהול. אחרת קל לשבור קשרים בין טבלאות, או להנפיק קישור שלא עובד, כי המפתח חייב להיווצר בקוד.

## אבטחה

- **מפתחות הקישורים:** 32 בתים אקראיים. ב-DB נשמר sha256 שלהם (לחיפוש) ועותק מוצפן ב-AES-256-GCM, שהמפתח שלו נגזר מ-`INTERNAL_API_SECRET` ולכן קיים רק בשרת. מי שמשיג גישה ל-DB לבד לא יכול להשתמש בקישורים.
- **זיהוי הלקוח:** השרת מזהה את הלקוח רק לפי המפתח. אין שום פרמטר בבקשה שמאפשר לגשת ללקוח אחר.
- **כותרות:** `Referrer-Policy: no-referrer` מונע מהמפתח לדלוף לאתרים אחרים. הדפים האישיים מסומנים `noindex`.
- **שיחות ניסיון:** מגיעות רק למספר שהוגדר בפקודה. הלקוח לא יכול לשנות אותו.
- **קול ומודל:** הלקוח שולח רק את המזהה של הקול בקטלוג. הספק, ה-ID, מודל הקול ומודל השפה נקבעים בשרת בלבד, וכל שדה נוסף בבקשה מתעלם. קול שלא בקטלוג או שכובה נדחה.
- **אורך ההנחיות:** ההנחיות נשלחות למודל בכל תור בשיחה, ולכן הנחיות ארוכות מייקרות כל דקה. לקוח מוגבל ל-8,000 תווים (`CUSTOMER_PROMPT_MAX` ב-`src/lib/validation.ts`). אם אדמין כתב לו הנחיות ארוכות יותר, הוא יכול לערוך אותן אבל לא להאריך. בפאנל הניהול המגבלה 20,000.
- **קולות פרימיום:** כל קול פעיל זמין לכל הלקוחות, כולל פרימיום. `tier` הוא כרגע רק תווית. אם קול מסוים יקר לך יותר, כדאי להשאיר אותו כבוי, או לבקש הרשאה לפי לקוח.
- **מפתח Vapi:** נמצא רק בשרת.
- **ה-API הפנימי:** מוגן בסוד משותף, עם השוואה בזמן קבוע.
- **Supabase:** ה-Data API כבוי ו-RLS פעיל, כך שגישה אפשרית רק עם הסיסמה של ה-DB.
- **audit_log:** כל עדכון בוט וכל שיחת ניסיון נרשמים עם IP.

## מבנה הקוד

```
src/
  app/
    b/[key]/page.tsx              הדף האישי של הלקוח
    admin/                        פאנל הניהול (admin/voices: מסך הקולות)
    api/voice-samples/[id]        GET  - דוגמת השמע של קול
    api/b/[key]/bot               PUT  - עדכן את הבוט
    api/b/[key]/test-call         POST - נסה את הבוט
    api/internal/usage            GET  - דקות לחיוב (למערכת שלך)
    api/internal/sync-calls       POST - סנכרון שיחות מ-Vapi
  components/bot-editor/          המסך
  lib/                            טיפוסים, ולידציה, קריאות מהדפדפן
  server/
    access.ts                     מפתח -> לקוח
    bot-service.ts                עדכון ושיחת ניסיון
    admin-service.ts              לקוחות, דמואים, קישורים (משמש את הפקודות ואת פאנל הניהול)
    voice-catalog.ts              קולות וייבוא מ-Vapi
    voice-admin.ts                מסך הקולות: הוספה, עריכה, דוגמאות, החלה על ה-assistants
    voice-samples.ts              יצירת דוגמאות שמע ושמירתן ב-DB
    elevenlabs-client.ts          ElevenLabs (רק לדוגמאות שמע)
    call-sync.ts                  סנכרון שיחות ומשך
    vapi-client.ts                הקריאות ל-Vapi
    vapi.ts                       המרה בין המסך לשדות של Vapi
  db/                             סכמה, חיבור, שאילתת דקות
scripts/                          פקודות ניהול, בדיקות, סביבה מקומית
drizzle/                          מיגרציות
```

## מה עוד לא קיים

- **קולות לפי לקוח:** כרגע כל קול פעיל זמין לכל הלקוחות. אין הרשאה לקול פרימיום ללקוח מסוים.
- **מסך שיחות ללקוח:** תמלולים וסיכומים.
- **מסך גרסאות** והחזרה לגרסה קודמת. הנתונים כבר נשמרים ב-`bot_versions`.
